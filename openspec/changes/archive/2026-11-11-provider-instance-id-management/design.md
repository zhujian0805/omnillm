## Context

See the proposal and delta specs. IDs are registry keys, SQLite parent keys, model-cache owners, and valid routing qualifiers. Immediate creation currently uses several derivation schemes, while OAuth flows can reserve or complete identities asynchronously. Most owned tables have `ON DELETE CASCADE` but not `ON UPDATE CASCADE`; virtual-model upstream provider references are not foreign keys. The registry has background persistence and providers can retain their instance IDs internally. A registry-only rename is therefore insufficient. Stored chat model IDs and external model strings can be ambiguous with native slash-containing model IDs.

## Goals / Non-Goals

**Goals:** Consistent new IDs and an explicit, safely persisted rename while preserving provider and routing behavior, with deterministic coverage across provider creation modes and restart.

**Non-Goals:** Bulk-renaming existing instances; rewriting external tool configurations, historical metering, arbitrary model strings, or ambiguous stored chat selections; changing provider type, display name, alias, or model identifiers; adding a CLI rename option as part of this UI/API request.

## Decisions

1. **Allocate UUID v4 once per new instance.** Use a cryptographically secure UUID generator already available in the project, in standard lowercase hyphenated form. Allocate and reserve uniquely at the appropriate point in each creation flow and consistently communicate the same canonical ID in pending and completed results. Retry generation on collisions and fail safely if randomness or reservation fails. This also applies to the default provider created during first server startup; an already persisted default retains its old ID. Existing-provider re-authentication and refresh never allocate or derive a new ID. Refactor account-, endpoint-, and credential-derived paths, including Copilot, ModelScope, OpenAI-compatible and Kimi credential refresh, without exposing credential fragments in new IDs. Alternative: type prefixes or shortened random IDs; rejected because their lengths vary or offer less collision resistance.

2. **Add a separate authenticated identity operation.** Use `PATCH /api/admin/providers/:id/identity` with `{ "new_id": "..." }` and return the new canonical `id`. Resolve the source with existing provider-reference rules. Treat an identical current ID, including a legacy ID outside the new syntax, as a no-op; otherwise trim input and enforce the delta's URL-safe 1–64 character syntax. Reject a target matching another canonical ID, alias, or display name under resolution semantics. Use client errors for malformed or conflicting requests and a retryable conflict when the provider is busy. Keep the existing name/alias endpoint unchanged. Alternative: overload the name endpoint; rejected to make the identity change and its compatibility impact explicit.

3. **Coordinate lifecycle, persistence, and routing with provider leases.** The registry owns a lifecycle coordinator for each registered instance. A caller acquires a shared lease atomically with obtaining the registered provider, verifies the identity is still current, and releases the lease only after its work no longer reads or writes that provider. Cover model discovery, generation and streaming, embeddings and evaluation, provider-scoped administration, credential refresh, and asynchronous authentication completion. An interactive re-authentication holds or reserves its provider lifecycle from flow start through completion, cancellation, failure, or expiry. For operations using several providers, acquire leases in a deterministic order, release every acquired lease on failure or cancellation, and never hold a global registry lock across upstream network calls. Rename obtains an exclusive non-blocking lease; if any operation or authentication flow owns the instance, return a retryable conflict without changing state. A lease belongs to the provider lifecycle rather than the mutable string ID, so a stale reference cannot acquire the renamed instance accidentally.

   Registry background persistence must participate: acquire the corresponding lease before taking or using a provider snapshot, recheck that its ID still maps to the same lifecycle under the registry lock, and never write a stale snapshot after a rename. Serialize administrative identity, alias, and name changes sufficiently to make target-conflict validation and publication atomic with respect to other identity changes. All provider access paths must be audited for lease coverage; test direct, multi-provider, streaming, refresh, OAuth, and background-save paths. Cache generation invalidation prevents already-started catalog fetches from publishing under an obsolete owner.

   Before opening the SQLite transaction, while exclusive access is held, prepare and validate an unpublished replacement provider using the old persisted state, then set its new ID before exposing it; add synchronized construction or setters to provider implementations as needed. This avoids reading the single-connection database from another connection while the transaction is open and avoids mutating objects already held by callers. Preflight every potentially fallible reconstruction step before commit. In one transaction create the new parent with preserved metadata, move owned children, rewrite exact `virtual_model_upstreams.provider_id` references, and remove the old parent. After commit, publish the prepared provider and rekey active and primary selection while readers remain excluded; invalidate both catalog generations and routing/model-state snapshots before releasing exclusive access. Publication must not introduce a fallible post-commit step. On any pre-commit failure retain the original registry and database; after a process crash following commit, startup reconstructs from committed state. Alternative: changing only a registry key, mutating an existing provider pointer, or holding a global mutex over network requests; rejected because these can race writes, expose mixed identities, or block unrelated traffic.

4. **Preserve routing semantics rather than guessing textual references.** Rewrite only the structured virtual-upstream provider field whose value exactly equals the old canonical ID; do not rewrite arbitrary model strings, chat selections, aliases, names, or historical metering. Existing virtual-model creation sometimes stores an instance qualifier inside `model_id`, so simply transferring `provider_id` leaves a former qualifier in the upstream model sent to the provider. During the same transaction, record a durable internal hint in the existing configuration table for each affected upstream whose stored model begins with the old canonical ID and a slash. Scope the hint to the upstream's stable row ID, its expected model string, and its current provider ID. Resolution uses that hint only for that exact upstream to preserve the same qualified-model behavior it had before the rename; it is not a provider alias and cannot redirect external references. Retain the original hint and update its owner on repeated renames. Remove hints transactionally when their upstream rows are replaced or deleted; reject a route with a mismatched or malformed hint rather than guessing. No database schema change is required.

   A model identifier beginning with the old ID can still be an advertised native identifier, so never change the stored model string or apply a hint to arbitrary requests. Warn operators before confirmation that external configuration and stored selections using the old qualifier may need manual updates. The previous ID is not retained as an automatic redirect; existing independently configured alias/name resolution remains unchanged. Alternative: blindly replace prefixes in model strings; rejected because it can change native namespaced models.

5. **Explicit edit and refresh.** Add a labeled instance-ID edit control to the existing provider card, with confirmation, validation, cancel behavior, and server-error feedback. Reload authoritative provider state after success rather than optimistically rekeying related client state. Preserve existing name/alias controls.

## Risks / Trade-offs

- [External references stop identifying the provider] → Warn before confirmation and describe manual updates; keep legacy IDs unchanged until explicitly renamed.
- [Existing clients assume provider type, username, or endpoint-derived ID for new instances] → Return the actual UUID in every creation/flow response and update in-repository callers and tests; explicitly document the behavior change.
- [In-flight writes or OAuth completion resurrect old identity] → Coordinate lifecycle operations and background writes; reject unsafe concurrent renames and exercise races with the Go race detector.
- [Duplicate identity or shadowed references] → Validate against the full current persisted and registered identity set and enforce transactional uniqueness.
- [Stored model strings cannot be safely distinguished from native namespaced models] → Leave them unchanged, warn the operator, and preserve complete-native-ID routing precedence.
- [Former virtual-upstream qualifiers stop resolving after rename] → Persist narrowly scoped per-upstream hints, remove them with the upstream, and test routing and cleanup across restart and repeated changes.
- [Credential or account data leakage] → Never derive generated IDs from secrets or account data; do not put credentials in errors or logs.

## Migration Plan

Deploy with existing SQLite IDs and references untouched. New providers receive UUIDs; each existing ID changes only on explicit operator confirmation. Exercise upgrades from populated databases, restart, and failed-transfer rollback. Rolling back application code does not automatically undo an already completed rename: the resulting valid IDs and transferred records remain stored, and external clients must use their current ID; restore a tested backup if a rollback requires the previous identity.
